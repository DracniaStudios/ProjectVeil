## SCRIPT

**[FOOTAGE: player walking normally through a hallway, calm pace, ambient stalker-game tension]**

Okay so this week almost broke the game in a way nobody would've caught by looking at it.

**[FOOTAGE: side-by-side split screen — left clip labeled "BEFORE", player sprinting across a room in slow motion; right clip labeled "AFTER", same sprint at normal speed]**

That's the same sprint animation. Same input. Same map. One of those is the game running correctly. The other one shipped for a few days and nobody noticed, because it doesn't look broken — it just looks slow.

That's what I want to talk about this week, plus two other fixes that are a lot easier to see.

**[FOOTAGE: title card / channel bumper, quick, no more than 2 seconds]**

Here's the problem, in one sentence: earlier this week I added a cap on delta time — the amount of game-time that passes each frame — to stop the game from taking a giant leap forward if it ever stalled for half a second. Good idea. Bad number.

And here's why it mattered: that cap ended up clamping *every single frame* instead of just the rare stall, which means for a few days the entire game — movement, physics, animations, minigame timers, everything that scales with delta time — was quietly running at half its intended speed at the framerate we actually ship at.

Let me back up and show you how that happened.

**[FOOTAGE: code editor, gameMain.cpp, the frame limiter line, zoomed enough to read]**

The idea behind a delta-time cap is simple. If your game is targeting 60 frames a second, each frame is supposed to represent about a sixtieth of a second of game time. But if something causes a hitch — loading a texture, garbage collection, whatever — and a frame takes, say, half a second to render, and you don't cap it, every frame-rate-independent system in your game just tries to simulate half a second of movement in one jump. Player teleports through walls, physics goes insane, all of that. So you cap it. You say "delta time can never report more than X seconds passed, even if it actually took longer."

The problem is what X was set to. It got set to one over one-twenty — a 120 FPS floor — meant to say "never let a frame count for more than 1/120th of a second." But the game's actual target framerate is 60 FPS, where every normal frame *already* represents 1/60th of a second — which is bigger than 1/120th. So instead of only kicking in on a real hitch, that cap was clamping down every normal frame to half its real length.

**[FOOTAGE: BEFORE/AFTER split again, this time footage of a physics object — a barrel or prop — falling under gravity, same drop height, two very different fall times]**

That's the part I actually caught it from — a falling object taking noticeably longer to hit the ground than it should have for its height. Once you know to look for it, it's everywhere: jump arcs feel floaty, sprint feels sluggish, minigame timers run long. None of it screamed "bug" on its own. Together, it's the whole game in slow motion.

**[FOOTAGE: code diff, the fix — cap changed from a 120 FPS ceiling to a 15 FPS floor]**

The fix flips what the cap is actually protecting against. Instead of a ceiling that's smaller than a normal frame, it's now a floor — the cap only engages once a frame drops below 15 FPS, which is the "something actually went wrong" case it was supposed to catch in the first place. Verified against the full test suite — 222 checks across 7 suites — and a normal frame at 60 FPS now passes through completely untouched.

**[FOOTAGE: BEFORE/AFTER sprint clips one more time, now both at correct, matching speed]**

Game's back to normal speed. On to the next one, which is a lot more visible.

**[FOOTAGE: player walking near a ledge, stepping off, falling into darkness below the map's geometry]**

This next bug is one of those "wait, why is the log lying to me" bugs. If the player — or really any entity — fell far enough below the map, the engine was *supposed* to recover them back to their spawn point. And the debug log agreed! It printed "recovering to spawn point," clear as day, every single time.

**[FOOTAGE: the player hanging motionless in the void below the map, camera showing nothing but darkness, for several seconds]**

And then nothing happened. The player just... stopped falling, and sat there. Forever. Stuck in the void, with a log message insisting it had fixed the problem.

**[FOOTAGE: code editor, Scene::clampObject, showing the actual teleport call sitting inside a comment block]**

Here's why: the code that actually teleports the object back to its spawn point was sitting inside a comment block. Somebody — okay, it was me, an earlier commit — had written the recovery logic, tested it, then a later refactor commented it out and never came back to finish the job. All that was left running was the log line and a velocity reset. It looked done. It logged like it was done. It just... wasn't wired up.

**[FOOTAGE: code diff — old GameMap spawnPoint field being removed, replaced with per-Entity spawn point]**

There was a second wrinkle: the recovery code was written back when the map itself tracked one single spawn point for the whole level. That's not how spawning works anymore — every entity now remembers its own spawn point individually — so I couldn't just uncomment the old code. It had to be rewritten to pull each entity's own recorded spawn location, with a safe fallback for anything that doesn't have one.

**[FOOTAGE: player falling off the same ledge, this time getting teleported back to a clearly visible spawn marker within about a second]**

Now when you fall off the map, you actually go somewhere. Same log message — now it's telling the truth.

**[FOOTAGE: player jumping off a low platform, landing, quick cut to the same jump with no sound at all]**

Last one's smaller, but it's the one you'll actually *feel* the most while playing. Jumping and landing had no sound at all. Every footstep did, every interaction did — landing was just silent, which is a weirdly noticeable gap once you notice it.

**[FOOTAGE: player jumping and landing, this time with the new landing sound, ideally in two different rooms to show it's positional]**

Landing now fires its own sound, triggered straight off the physics component the moment it detects a landing — not bolted on somewhere else and hoping it stays in sync. And while I was in there, audio in general got two upgrades worth mentioning: sounds now actually come from the position of whatever object is making them in 3D space, instead of playing flat no matter where you are relative to the source, and the audio manager finds every sound file and bank by scanning the folders recursively instead of needing every single asset registered by hand somewhere. Drop a file in the right folder, it's just there.

**[FOOTAGE: quick montage — sprinting at correct speed, falling off the map and recovering, jumping and landing with sound, all back to back]**

So that's the week: a speed bug nobody would've clocked by eye, a recovery system that was lying about doing its job, and landing finally making a sound. None of these are flashy new features — they're the game actually doing what it already claimed to be doing.

**[FOOTAGE: current build running normally, maybe a short loop of the stalker AI tracking the player through a hallway, to tease what's next]**

Collision detection also got consolidated into one place this week as part of chasing that speed bug down, which is groundwork for some Stalker AI behavior changes I'm not ready to show yet — that's next.

If you want to see this stuff before it ships, or you want to poke at the half-speed footage yourself frame-by-frame, the repo's public and linked below. Subscribe if you want the next one when it's out, and drop a comment if there's a specific system you want me to dig into next. See you next week.
